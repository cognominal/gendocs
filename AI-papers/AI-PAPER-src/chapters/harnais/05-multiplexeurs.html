VII. Multiplexeurs et gestionnaires d'agents

7.1 Pourquoi plusieurs agents à la fois

Un agent de code travaille lentement à l'échelle humaine : une tâche sérieuse prend de cinq minutes à une heure, pendant lesquelles l'humain n'a rien à faire, sinon répondre de temps en temps à une demande de permission. La réponse naturelle est d'en lancer plusieurs : un agent corrige un bug, un deuxième écrit des tests, un troisième explore une idée, un quatrième relit le travail des autres. En 2026, beaucoup de développeurs travaillent avec trois à dix agents ouverts en même temps. Cela pose trois problèmes nouveaux :

  • voir : savoir d'un coup d'œil quel agent travaille, lequel attend une réponse, lequel a fini ;
  • isoler : empêcher deux agents de modifier les mêmes fichiers en même temps ;
  • coordonner : faire passer une information ou une tâche d'un agent à l'autre, et comparer leurs résultats.

Trois générations d'outils y répondent : les multiplexeurs de terminal, conçus bien avant les agents ; les gestionnaires d'agents, apparus en 2025 ; et des environnements comme tuios qui combinent les deux.

7.2 Les multiplexeurs de terminal

Un multiplexeur de terminal fait tourner plusieurs sessions dans une seule fenêtre et les garde en vie quand on se déconnecte. GNU Screen (1987) a créé le genre ; tmux (Nicholas Marriott, 2007) l'a modernisé avec ses panneaux, ses sessions nommées et une interface scriptable ; zellij (2021, écrit en Rust) y ajoute une interface plus découvrable et des plugins. Trois de leurs fonctions servent directement aux agents :

  • la persistance : un agent lancé dans tmux sur un serveur continue de travailler quand l'ordinateur portable se met en veille, et on le retrouve depuis un autre poste ;
  • les panneaux : quatre agents côte à côte, avec un shell pour vérifier leurs résultats ;
  • le pilotage par script : tmux send-keys tape du texte dans un panneau, et tmux capture-pane en lit le contenu. Un agent peut donc piloter un programme interactif, ou un autre agent, comme le ferait un humain.

Ce dernier point a fait de tmux un outil d'agent à part entière. Terminus 2, l'agent neutre de Terminal-Bench (fiche 115), n'a qu'une session tmux comme interface : il tape des touches et lit l'écran, ce qui lui permet d'utiliser vim, un débogueur ou un REPL. Pi, qui n'a pas de sous-agents, recommande de lancer une autre instance de lui-même dans un panneau tmux.

7.3 Les worktrees : un dépôt, plusieurs copies de travail

Deux agents qui modifient le même dossier se marchent sur les pieds : l'un relance les tests pendant que l'autre réécrit un fichier. La solution standard est le worktree git (git 2.5, 2015). Un même dépôt peut avoir plusieurs copies de travail, chacune dans son dossier et sur sa branche, qui partagent l'historique sans dupliquer les objets. On crée un worktree par agent, chaque agent travaille sur sa branche, puis on fusionne ce qui est bon. Claude Code, Codex et la plupart des gestionnaires d'agents créent désormais eux-mêmes ces worktrees.

Les worktrees ne règlent pas tout. Chaque copie doit installer ses dépendances et lancer ses propres serveurs de développement, sur des ports différents. Deux agents qui touchent au même fichier produisent un conflit au moment de la fusion. Et l'humain doit relire autant de branches qu'il y a d'agents.

7.4 Les gestionnaires d'agents

Une famille d'outils apparus en 2025 combine les deux briques précédentes et y ajoute la connaissance des agents :

  • Claude Squad (2025, open source) : une interface en terminal qui crée, pour chaque tâche, une session tmux et un worktree, y lance Claude Code, Codex, Aider ou un autre harnais, et affiche la liste des sessions avec leurs diffs ;
  • Conductor (2025) : une application macOS qui fait de même avec une interface graphique, autour de Claude Code et de Codex ;
  • des tableaux de type kanban (Vibe Kanban), où chaque carte devient une tâche confiée à un agent ;
  • les gestionnaires intégrés aux harnais eux-mêmes : la fenêtre d'agents de Cursor, les applications de bureau de Codex et de Claude, qui affichent plusieurs sessions parallèles ;
  • de nouveaux multiplexeurs pensés pour les agents, comme herdr ou muxel, et tuios, décrit ci-dessous.

7.5 tuios : un multiplexeur qui connaît les agents

tuios (« Terminal UI Operating System »), écrit en Go par Gaurav Gosain sous licence MIT, est un gestionnaire de fenêtres en terminal : des panneaux en mosaïque ou flottants, des espaces de travail, un démon qui garde les sessions en vie, et un serveur SSH pour s'y connecter à distance. Ce qui le distingue de tmux est qu'il reconnaît les harnais qui tournent dans ses panneaux (Claude Code, Codex, Gemini CLI, Pi, OpenCode, etc.), soit en analysant l'écran, soit en recevant leurs hooks. Il en tire plusieurs fonctions :

  • l'état de chaque agent (travaille, attend une réponse, a fini, a échoué) est affiché sur le panneau et dans une barre latérale ;
  • une boîte de réception (Inbox) rassemble tout ce qui attend l'humain : demandes de permission, questions, fins de tâches. On peut répondre à une demande sans aller dans le panneau (tuios respond), y compris depuis un téléphone appairé par QR code ;
  • la messagerie entre agents : un agent peut laisser un message à un autre (tuios send-agent-message), lui poser une question et attendre la réponse (tuios ask-agent), confier une tâche à un agent enfant (tuios delegate), ou poser une question à l'humain avec des réponses au choix (tuios ask-human) ;
  • l'éventail : tuios fan 3 "…" --agent claude,codex,gemini crée trois worktrees du dépôt, lance un harnais différent dans chacun, tape la même consigne et les affiche côte à côte. C'est un petit banc d'essai personnel, à la manière de Terminal-Bench, sur ses propres tâches ;
  • les machines distantes : les worktrees peuvent vivre sur un autre hôte, et leurs résultats se rapatrient (tuios worktree pull).

tuios s'expose aussi aux agents eux-mêmes : en ligne de commande, comme serveur MCP, et par une skill qui explique à un agent comment lire les autres panneaux, attendre la fin d'un travail ou rendre compte de son propre état. L'agent n'est plus seulement dans le multiplexeur : il peut s'en servir.

7.6 Trois rôles

Ces outils se distinguent par ce qu'ils savent des agents :

RôleExemplesCe qu'il apporte
Multiplexeurscreen, tmux, zellijpersistance, panneaux, pilotage par script
Gestionnaire d'agentsClaude Squad, Conductorworktree par tâche, liste des sessions, diffs
Multiplexeur d'agentstuios, herdrétats, Inbox, messagerie, éventail

La limite de tous ces outils n'est pas technique. Le goulot d'étranglement devient l'attention humaine : lire les diffs, juger les approches, décider quoi fusionner. Dix agents produisent dix fois plus de code à relire, et dix fois plus de factures de jetons. Les praticiens qui en tirent le meilleur parti donnent aux agents des tâches indépendantes et bien définies, font relire le travail d'un agent par un autre avant de le lire eux-mêmes, et gardent un agent pour la tâche qu'ils suivent de près.
